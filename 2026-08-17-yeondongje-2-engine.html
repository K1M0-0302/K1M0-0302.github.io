2026. 8. 17. · 연동제 계산기

연동제 계산기 ② 결정론 규칙엔진과 3분 퍼널

  • Next.js
  • TypeScript
  • Vitest
  • react-pdf
  • Supabase
  • 규칙엔진

①편에서 "판정과 계산은 규칙엔진, LLM은 보조"라는 원칙을 세웠다. 이 글은 그 원칙이 코드로 어떻게 옮겨졌는지 정리한다. 구현은 팀 저장소에 쌓인 팀 작업이고, 이 구간에 내 계정(KIM00) 커밋은 없다. 아래 내용은 저장소의 코드·테스트·문서를 근거로 정리했다.

8월 16일 — PDF 폰트 스파이크부터

계획의 Phase 1 첫 작업은 규칙엔진이 아니라 PDF 한글 폰트 스파이크였다. 결과물이 원청에 내미는 PDF인데, 배포 환경에서 한글이 깨지면 나머지가 다 소용없기 때문이다. @react-pdf/renderer에 Pretendard(OFL)를 넣어 검증을 통과시킨 뒤에 엔진을 시작했다.

같은 날 순서대로 다음이 들어갔다.

  • 규칙엔진(lib/engine.ts): 거래유형으로 하도급법 / 상생협력법 / 부적용을 가르고, 적용 주체 요건 → 주요 원재료 10% 비중 → 예외 4종 → 에너지비용 분기 → 약정 유무에 따른 2모드 계산 순으로 판정한다. 파일 첫 줄에 "LLM은 이 파일에 관여하지 않는다"고 적혀 있다.
  • 조문 스냅샷(lib/statutes.ts): 결과에 붙는 조문은 law.go.kr 원문을 스냅샷으로 넣었다. 모델이 조문을 지어낼 여지를 없애려는 것이다.
  • 가격 스냅샷: ECOS 생산자물가지수를 실시간 호출하지 않고, 수집 스크립트로 받아 data/price-snapshots.json에 커밋한다. 같은 입력이면 언제 돌려도 같은 결과가 나온다.
  • 자재 매칭: 1차는 결정론 별칭 사전이고, 사전에 없을 때만 LLM이 근사 매칭을 하며 "AI 추정" 라벨을 붙인다. 한국어 자재 규격 골든셋 30건에서 30/30, 함정 문항 오매칭 0/5를 확인했다.
  • 계약서 자동 입력: 텍스트 붙여넣기나 텍스트 PDF 업로드 → LLM 구조화 추출 → 사용자가 확인한 뒤에만 폼에 반영한다. 계약서 원문은 저장하지 않는다.

8월 17일 — 토스식 스텝 퍼널로 전면 개편

8월 16일 첫 UI를 배포한 다음 날, 대상 실무자가 휴대폰에 익숙한 40~60대라는 점을 감안해 하루 만에 표현 계층을 전부 갈아엎었다. 흐름은 소개 → (계약서 추출) → 당사자 → 계약 → 자재 → 계산 연출 → 결과 → 원청 제출 자료 순서다. 원칙은 엔진·조문·경계값·PDF 내용은 그대로, 화면만 바꾼다였다. 이를 지키려고 퍼널이 조립한 입력이 기존 폼과 같은 엔진 입력을 만드는지 확인하는 패리티 테스트 12개를 추가했고, 테스트는 56/56(엔진 44 + 퍼널 12)으로 통과했다.

결과 화면은 큰 숫자(조정액) 하나를 먼저 보여 주고, 바로 아래에 판정 경로를 번호로 풀어 쓴다. 비중이 10%에 못 미치는 자재는 왜 조정액이 없는지 문장으로 알려 준다. 위 캡처는 합성 목계약서(전기 공사)로 배포 사이트를 돌린 화면이다. 계약서 조항대로 기준시점을 2026-08로 두면 아직 비교할 지수가 없어 "계산 시점이 아니에요"가 뜬다. 그래서 기준시점을 2026-01로 앞당겨 찍었다.

마지막 단계에서는 1쪽 근거자료 PDF와 조정협의 신청 공문 초안을 만든다. PDF에는 적용 법령 판정과 판정 경로, 자재별 기준·비교 지수와 변동률, 조정액, 근거 조문 원문, 가격 출처와 수집일, 면책 문구가 들어간다.

8월 25일 — 폐쇄망 박스 구상과 "읽기만 맡기기"

원가와 자재 내역은 영업비밀이라 외부 클라우드 AI에 올리기 꺼려진다는 점에 착안해, 같은 엔진을 인터넷 없는 기기에서 돌리는 계획(Phase 3)을 세웠다. 기기를 사기 전에 갖고 있던 휴대폰(Galaxy A34)에서 먼저 쟀다.

  • 모델: Qwen2.5-1.5B-Instruct Q4_K_M(1.04GiB), llama.cpp + GBNF 문법으로 출력 JSON 형식을 강제
  • 정형 필드 12개 추출은 12/12 정확했다.
  • 하지만 조항의 법적 분류(연동약정이 있는지, 미연동 합의인지)는 0/2였다.

그래서 역할을 다시 그었다. 소형 모델은 근거 문장 추출까지만 하고, 분류는 "적용하지 아니" 같은 부정 패턴을 보는 결정론 분류기(lib/clause-classify.ts)가 확정한다. 같은 두 케이스를 다시 돌려 2/2를 맞췄다.

8월 29일 — 경계값 하나를 원문으로 다시 잡다

건설업 소기업 경계값이 60억 원으로 들어가 있었는데, 중소기업기본법 시행령 별표 3 원문을 직접 열어 보니 건설업은 80억 원이었다. 60억은 도매·소매업 값을 잘못 읽은 것이었다. 엔진 계산 로직은 바뀌지 않고 라벨과 안내 문구만 틀렸던 결함이었고, 정정 기록(CORRECTIONS.md)에 남긴 뒤 테스트 69/69로 마무리했다.

기술스택

  • Next.js 16 · React 19 · TypeScript · Tailwind CSS 4 (Vercel 배포)
  • @react-pdf/renderer + Pretendard(PDF 한글), unpdf(PDF 텍스트 추출)
  • Vitest(엔진 경계값·정답지 교차검증·퍼널 패리티·조항 분류 테스트)
  • 한국은행 ECOS 생산자물가지수(배치 스냅샷), OpenRouter(추출·매칭 LLM), Supabase(익명 계산 이력)
  • 온디바이스 실측: llama.cpp, Qwen2.5-1.5B-Instruct GGUF Q4_K_M, GBNF

배운 점

  • 가장 위험한 기술 가정(배포 환경의 PDF 한글)을 맨 먼저 검증해, 끝에 가서 막힐 위험을 처음에 지웠다.
  • "화면만 바꾼다"는 약속은 패리티 테스트로 지켜야 실제로 지켜진다.
  • 작은 모델은 읽기는 잘하지만 법적 판단은 못 했다. 모델을 키우기보다 판단을 규칙으로 옮기는 편이 정확하고 설명 가능했다.
  • 경계값 하나도 원문을 직접 열어 봐야 한다. 리서치 요약을 그대로 믿었다가 틀렸다.
