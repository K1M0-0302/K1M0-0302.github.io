소형 언어모델을 13구역 지도로 나눠 배우기

  • SLM
  • llama.cpp
  • GGUF
  • 도메인 학습
  • Claude Code

연동제 계산기에는 작은 언어모델(Qwen2.5-1.5B Q4)을 오프라인 박스에 올리는 작업이 있다. 이 작업에는 Q4_K_M, 프리필, KV 캐시 같은 말이 계속 나왔다. 리서치 보고서도 여러 편 쌓였지만, 보고서는 질문 하나에 답할 뿐 분야 전체에서 어디가 비어 있는지는 보여 주지 않는다. 그래서 분야 전체를 지도로 먼저 그리고, 구역 단위로 배우기로 했다.

9월 1일 — 학습용 폴더 에이전트 설치

도구로는 다른 사람이 만든 비공개 스킬 두 개를 받아 썼다. 지도를 그리는 kartierung과, 지도의 구역을 하나씩 도는 rundgang이다. 설치하면서 내가 고친 것은 두 가지다. 원본은 외부 리서치 도구를 거쳐 웹 조사를 하게 되어 있었는데, 이를 Claude가 직접 WebSearch·WebFetch로 조사하도록 바꿨다. 그리고 원작자 환경의 경로를 이 머신 경로로 맞췄다.

9월 10일 — 지도 확정: 표준 구도에 내 프로젝트 별점

지도의 뼈대는 그 분야 전문가들이 나누는 방식을 따르고, 별점은 내 프로젝트 기준으로 매긴다. 그래서 배우지 않을 구역도 지도에 위치와 이유를 남긴다.

렌즈로 쓴 자료는 세 가지다.

  • 9월 8일에 쓴 sLLM·SBC 리서치 보고서 — 이론·시장 층
  • 연동제 계산기 저장소 — 실전 운영 층
  • 8월 25일 갖고 있던 갤럭시 A34에서 1.5B 모델을 llama.cpp로 돌려 본 실측 원자료 — 프롬프트, GBNF 문법, 응답 JSON

결과는 13구역이다. 정의와 경계부터 프리필·디코드, 하드웨어와 속도, 압축, GGUF와 양자화 등급, 런타임, 구조화 출력, 한계와 경계 설계, 모델 고르기까지 아홉 구역이 ★★★이다. 오프라인 박스·적응·평가가 ★★, 아키텍처가 ★이다. 지도는 큰 덩어리 넷으로 묶었다. 무엇을 다루는지 정하기, 속도와 메모리가 정해지는 곳 보기, 모델을 예산 안으로 밀어 넣기, 경계를 긋고 고르기다.

각 구역에는 "프로젝트 접점"을 파일:줄 단위로 붙였다. 예를 들어 하드웨어 구역에는 라즈베리파이 5의 메모리 대역폭(STREAM 11.20 GB/s)에서 디코드 상한 약 11.2 tok/s를 미리 계산한 문서 줄이 걸려 있다. 로컬 자료에 없는 것은 없다고 적었다. GGUF·K-quant 구역은 리서치 보고서에 "GGUF"가 한 번도 나오지 않아 "로컬 공백"으로 표시했다.

같은 날 — 구역 13편의 개념 해설

구역 1 첫 개념(파라미터)을 대화로 배우던 중에 방향을 바꿨다. 13구역 전체를 HTML 해설서로 먼저 만들어 두기로 한 것이다. 결과는 13편, 개념 86개, 확인 문제 168개다. 개념마다 같은 틀을 썼다. 정의 한 줄, 왜 그런가, "이 프로젝트에서는 이렇게 나타난다", 함정 순서다.

구역 8(한계와 경계 설계)에서 프로젝트와 개념이 가장 직접 맞물렸다. 모델 카드 표를 보면 작은 모델은 지식 회상에서는 크게 뒤지고, 형식에 맞춰 옮기는 일에서는 격차가 작다. A34 실측도 같은 모양이었다. 정형 필드 추출은 12/12였지만 조항의 법적 분류는 0/2였다. 연동제 계산기가 판정·계산을 LLM에서 떼어 결정론 엔진에 맡긴 결정을, 해설에서는 이 "회상 대 형식 처리" 개념과 연결해 정리했다.

13편의 스타일이 갈라지지 않게 생성기 두 개를 두었다. 첫째는 1편의 <style>을 단일 원본으로 삼아 2~13편 본문에 씌우는 스크립트다. 둘째는 13편을 한 페이지로 합치는 스크립트로, 상단 구역 칩, 하단 이전/다음, #z07 같은 해시 이동을 지원한다. 13편이 각각 id="c1"을 써서 합치면 충돌했다. 그래서 z07-c1처럼 구역 접두를 붙여 해결했다.

막힌 점

  • 구역 1 해설에서 Q4_K_M 파일의 파라미터당 비트수를 처음 5.4비트로 적었다. 1.04GiB(약 8.93×10⁹비트)를 15.4억으로 나누면 약 5.8비트가 맞아서 정정했다. 통상값보다 큰 이유(어휘가 많아 임베딩 비중이 크다)는 파일 내부를 열어 본 것이 아니므로 추정이라고 표시했다.
  • 프로젝트 문서 하나가 라즈베리파이 5 수치를 "실측"이라 불렀다. 그런데 같은 문서 뒤쪽은 공개 벤치마크 환산이라고 밝히고 있었고, 보드는 아직 사지 않은 상태였다. 이 사례는 평가 구역(12)의 "실측과 환산을 구분해 기록하기" 예시로 지도에 남겼다.

지금 상태

지도와 해설서는 만들었지만, 구역 통과(✅)는 아직 0개다. 구역 1의 확인 문제는 풀기 전이다. 문제를 다 풀어 통과한 구역만 ✅를 받는 규칙이라, 진도는 지도 문서에 그대로 남아 있다.

기술스택

  • Claude Code 폴더 에이전트 + kartierung·rundgang 스킬
  • HTML/CSS 해설서, Python 생성기(스타일 단일 원본·합본)
  • 학습 대상 개념: llama.cpp, GGUF/K-quant, GBNF 구조화 출력, KV 캐시

배운 점

  • 리서치 보고서를 여러 편 쌓는 것과 분야를 아는 것은 다르다. 지도를 그리니 어느 구역에 로컬 근거가 0건인지가 먼저 보였다.
  • 개념마다 내 프로젝트의 파일:줄을 붙이니, 이미 내린 설계 결정의 이유를 개념 단위로 다시 설명할 수 있게 됐다.
  • 만드는 것과 배우는 것은 다르다. 해설서 168문제는 만들어졌지만 아직 풀지 않았다. 학습 성과는 정량으로 확인되지 않았다.
