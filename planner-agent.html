MVP 계획 에이전트 (planner-agent)

개요

아이디어를 받아 MVP 구현계획서 한 회차를 생산하는 폴더형 에이전트. 주제선정 → 리서치 → 구현계획서(여기) → UI/UX → 최종구현으로 이어지는 다중 에이전트 사이클의 한 단계를 맡는다.

배경과 문제의식

MVP는 한 번 만들고 끝나지 않는다 — 실사용자 소수에게 주고 피드백을 받아 다음 회차로 잇는 반복이 본질이다. 그런데 세션이 바뀌는 AI 에이전트는 회차 사이의 맥락을 잃기 쉽다. 이 에이전트는 반복 원장(LEDGER)을 중심에 놓아 그 문제를 푼다.

구조와 개념

  • 회차 단위 산출물: 회차마다 plan\<NN-주제>\를 파고 Claude Code 구현용 plan.md와 Codex(UI/UX 담당)용 ui-brief.md를 나란히 둔다 — 납품 대상이 다른 두 문서를 한 회차로 묶는 구조다.
  • 반복 원장 LEDGER.md: 회차 이력과 받은 피드백이 쌓이는 단일 파일. "새 세션은 원장부터 읽는다"가 첫 규칙이다.
  • 구두 피드백 원칙: 피드백 수집 장치를 따로 만들지 않는다. 사용자가 MVP의 단점을 말하면 스킬 트리거와 무관하게 그 자리에서 해당 회차의 "받은 단점"에 받아 적는다.
  • 결정의 정본화: 설계 결정 12개(가설 검증 우선, 완료 정의 = 무료 배포 URL, 결정 잠금, 브리프 납품 계약 등)는 별도 정본 파일에 있고, CLAUDE.md에 요약을 다시 적지 않는다 — 두 곳에 적으면 갈라진다는 원칙.
  • 지연 로딩 규율: 계획서 작성 규율(스펙 실패 패턴 6종)과 무료 티어 스택 수치는 템플릿을 읽을 때만 paths-scoped rule로 로드된다 — 매 세션의 컨텍스트 비용을 아끼는 설계.

개발 과정

  • 2026-08-06 MVP 구현계획서 방법론 리서치를 근거로 설계 결정을 확정했다. 벤더링 후보 (github/spec-kit, gsd-core, shadcn-ui 등)를 조사했지만 전부 보류했다 — 필요가 증명되기 전에 남의 repo를 들이지 않는다는 원칙.
  • 다중 에이전트 분업(리서치는 위임, UI/UX는 Codex, 구현은 Claude Code)을 전제로 자기 역할을 "구현계획서 한 회차"로 좁게 잘랐다. 진행 관리나 다른 에이전트 지휘는 명시적으로 범위 밖이다.

현재 상태

  • 장비(스킬·rule·템플릿·설계 결정 정본)는 갖춰졌으나, 활성 프로젝트가 미정이라 실운행 회차는 아직 없다. 심사위원 데모 모드 같은 마감 상황 규율은 첫 해커톤 마감 때 실측으로 적립할 예정.

기술스택·도구

Claude Code(스킬·paths-scoped rules) · 다중 에이전트 분업(Codex CLI와의 납품 계약 문서 형식)

배운 점

  • 에이전트의 역할은 좁을수록 강하다 — "계획서 한 회차"로 범위를 자르고 앞뒤 단계는 계약(브리프 형식, 원장)으로 잇는 편이 만능 에이전트보다 유지보수하기 쉽다.
  • 정본은 한 곳에만 둔다. 요약 복제는 편리해 보이지만 갈라지는 순간 어느 쪽이 맞는지 아무도 모른다.
