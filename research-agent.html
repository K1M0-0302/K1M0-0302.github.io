리서치 에이전트 (research-agent)

개요

주제 하나를 받아 웹과 NotebookLM 정리본을 조사해 출처가 강제된 한국어 리서치 보고서를 내는 폴더형 에이전트. quick/deep 두 등급으로 조사 규모를 조절하고, 인용 검증 서브에이전트를 통과해야 완료로 친다.

배경과 문제의식

LLM 리서치의 고질병은 그럴듯하지만 출처 없는 문장이다. 이 에이전트는 "출처 없는 사실 주장은 보고서에 못 쓴다"를 규칙이 아니라 파이프라인으로 만들었다 — 사람이 아니라 검증기가 지키는 규율.

구조와 개념

  • 등급제: quick(검색 ≤8회, 출처 5~8개, 서브에이전트 0) / deep(하위질문 3~5개 × 각 1 서브에이전트, 출처 15~40개, 고유 도메인 ≥5). 두 등급 모두 research-reviewer 통과가 완료 조건.
  • 인용 강제: 본문은 한국어, 출처는 원어 제목·URL·접근일. 따옴표 안 문구는 출처 원문 그대로. 리뷰어가 인용 정확도·유효 인용·문장 커버리지 지표 3개를 산출해 보고서 frontmatter에 남긴다.
  • 기계 검사 이중화: check_report.py가 PostToolUse hook으로 보고서 저장 때마다 형식을 검사하고, wayback_snapshot.py가 출처 URL의 Wayback Machine 스냅샷을 떠 링크 부패에 대비한다 (멱등, 21초 간격 익명 저장).
  • 검색 도구 계층: 내장 WebSearch/WebFetch + 원격 MCP(exa는 키 없이 전문 26,469자 수집 실측, jina는 키 필요). 오판이 실측된 도구(guess_datetime_url)는 명시적으로 금지 목록에 있다.

개발 과정

  • 가장 극적인 사건은 guard hook의 유령 버그다. 2026-08-22, 산출물 위치를 강제하는 PreToolUse hook이 차단하지 않는 문제를 "세션 중 추가한 hook은 등록되지 않는다"로 해석했다. 2026-08-24 재조사에서 이 해석이 틀렸음이 드러났다 — hook은 등록·실행되고 있었다. 진짜 원인은 Windows PowerShell 5.1이 stdin을 OEM(CP949)으로 읽는 것: hook JSON의 경로에 든 한글 사용자명 나 (EB 82 98)의 마지막 바이트가 뒤따르는 백슬래시(5C)를 트레일 바이트로 삼켜 JSON이 깨졌고, catch { exit 0 }으로 조용히 통과했다. 즉 이 가드는 그날까지 한 번도 막은 적이 없었다. stdin을 바이트로 읽어 UTF-8로 디코드하는 방식으로 고쳤고, 수정 직후 같은 세션에서 차단이 실측됐다. 자가 테스트도 stdin에 UTF-8 바이트를 직접 주입하는 방식으로 다시 썼다.
  • 2026-08-24 deep 등급 실운행: 서브에이전트 5개가 출처 83건을 수집, 25건으로 선별, 리뷰어가 서브에이전트가 의역한 인용구 4건과 맥락 뒤틀림 1건을 잡아내 수정 후 통과.
  • Wayback 스냅샷 도구를 붙이면서 제목의 | 문자가 마크다운 표 열을 밀어 깨뜨리는 버그를 잡아 TDD로 수정했다.

현재 상태

  • 검증됨: 가드 자가 테스트 12/12(2026-08-27 기준 — 08-24의 10/10에서 케이스가 추가됐다), 보고서 검사기 unittest 15/15, 스냅샷 도구 unittest 10/10, /research-report 실운행 2회(quick·deep 각 1회, 리뷰어 통과), exa MCP 실호출.
  • 미검증(2026-08-24 기준): 서브에이전트가 MCP 도구를 실제로 쓰는지는 다음 세션 확인 대기, 브리핑 템플릿의 다크 모드 육안 검증.

기술스택·도구

Claude Code(스킬·서브에이전트·PreToolUse/PostToolUse hook) · PowerShell 5.1 + Python 3.11 (검사기·스냅샷 도구, unittest) · 원격 MCP(exa·jina) · Wayback Machine SPN2 API · Notion MCP(읽기 전용)

배운 점

  • "hook이 등록 안 됐다"와 "hook이 조용히 실패한다"는 겉보기가 같다 — 원인 규명 없이 결론을 적으면 다음 세션이 틀린 해석 위에서 일한다. 마커를 심어 실행 여부부터 실측하는 것이 맞았다.
  • 검증기의 검증(자가 테스트)도 같은 인코딩으로 입력을 넣어야 버그를 재현한다 — 08-22의 테스트는 OEM 인코딩으로 넣어 버그를 못 잡았다.
